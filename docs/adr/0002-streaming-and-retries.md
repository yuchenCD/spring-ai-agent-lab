# ADR-0002：流式输出与重试的边界

- 状态：已采纳
- 日期：2026-11-24

## 背景

v0.1 的 `/chat` 与 `/chat/stream` 都拿完整回复再返回；`/chat/stream` 只是把"工具步进"发出去，不是真正的 token 流。
同时，LLM 网关偶发 429/5xx 时整个请求会直接失败。

v0.2 要解决两件事：**让回答像打字一样流出来**，以及**瞬时失败自动恢复**。

## 决策

### 1. 流式放在 `LlmClient` 层，而不是控制器层

`LlmClient.stream(messages, tools, onToken)` 返回**聚合后的完整 turn**：文本 delta 边到边回调，工具调用分片按
`index` 聚合后随结果一起返回。这样：

- Agent 循环仍是"拿到一个 turn → 判断有没有工具调用"的简单状态机，不需要把流式状态泄漏到循环外；
- 控制器只负责把 `onToken` 映射成 SSE `token` 事件；
- 非流式 provider（如 Mock）用接口默认实现即可：整段文本作为单次 delta。

### 2. 工具调用并行，但结果顺序固定

同一 assistant turn 可能返回多个 tool call。用 Java 21 虚拟线程并发执行，`invokeAll` 带批次截止时间；
结果按原始调用顺序收集，再按顺序写回消息与事件。理由：

- 工具之间通常互不依赖，串行会白白放大尾延迟；
- 模型消息里 `tool` 结果必须与 `tool_calls[].id` 对齐，顺序固定可以保证重放语义；
- 超时/异常统一转换成 `ERROR: ...` 观察，让模型自己决定下一步，而不是让整个 HTTP 请求 500。

### 3. 重试装饰器，且"已输出即不重试"

`RetryingLlmClient` 包住真实 provider，只重试连接错误与 HTTP 429/5xx，指数退避 + 抖动。
流式调用一旦已经向调用方输出过 token，就**不重试**：否则客户端会看到重复文本，或接到前后矛盾的两个回答。

## 代价与边界

- 流式解析自己维护（SSE 方言相对稳定，风险可控）；未实现 `usage` 统计与 `finish_reason` 透传，留到 v0.4 评测时补。
- 工具并行沿用"一个批次一个截止时间"的语义，不是严格的逐工具 deadline；已能覆盖慢工具拖垮单轮的情况。
- 重试按错误文本分类（`LlmException` 携带 HTTP 状态），没有引入 Resilience4j 等依赖；如果错误种类继续增加，届时可以抽象成策略而非装饰器。

## 何时重新考虑

- 需要区分"流式输出中失败可续传"的产品语义时（需要服务端会话级 buffer 与断点续传协议）；
- 需要按工具粒度设置超时、重试、限流时。
