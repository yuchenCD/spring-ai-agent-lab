# ADR-0001：直接用 JDK HttpClient，而不是引入 Agent 框架

- 状态：已采纳
- 日期：2026-11-23

## 背景

Java 生态已有 Spring AI、LangChain4j 等 Agent/LLM 框架，也可以使用各家厂商 SDK。
本项目的目标不是最快做出产品，而是把 Agent 的每一层拆开、可测试、可替换。

## 决策

对 DeepSeek（OpenAI 兼容）接口直接使用 JDK `java.net.http.HttpClient` 手写请求与解析：

1. 不引入 Spring AI / LangChain4j / OpenAI SDK。
2. 自定义极小的 `LlmClient` 接口（`complete(messages, tools)`），实现只有两类：HTTP 实现与测试用脚本化实现。
3. 消息、工具调用、工具声明用少量 record 表达，字段与协议一一对应。

## 理由

- **可观测**：请求体与响应解析都在一个文件里，排查 400/429/协议变更时不需要翻框架源码。
- **可测试**：用 JDK 自带的 `com.sun.net.httpserver.HttpServer` 就能做协议级测试，不加测试依赖、不碰网络。
- **可替换**：`LlmClient` 是唯一接缝；换成 Spring AI 或别的 SDK 时，改动面就只有这个实现类。
- **教学价值**：这是"实验场"，隐藏协议细节会削弱它作为学习与面试素材的价值。

## 代价

- 需要自己维护协议解析（OpenAI 兼容格式相对稳定，风险可控）。
- 没有框架带来的工具编排、重试、可观测性等现成能力；这些后续按需补，而不是一次性押注框架。
- 多模态、结构化输出等高级能力需要自行扩展。

## 何时会重新考虑

- 需要多 Provider 的复杂能力矩阵（多模态、结构化输出、批量、缓存）且自研成本显著上升时；
- 需要框架级的可观测/评测/追踪体系时。

届时按 ADR 记录新的取舍，而不是悄悄替换。
